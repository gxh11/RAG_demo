构建一套具备结构化解析、表格原子化与父子索引的完整 RAG 系统，前端、后端与 AI 管道各自的职责划分及全流程协作如下：

---

### 一、 前端（Frontend）职责

前端核心解决**用户输入交互**、**长耗时状态反馈**与**多模态/结构化结果展示**：

1. **文档摄取交互**
* **文件校验与上传**：提供拖拽与点击上传，前端校验文件后缀（`.pdf`）与单文件大小限制，封装为 `multipart/form-data` 发送。
* **多阶段任务状态追踪**：由于 PDF 解析与向量化耗时较长（通常 5–30 秒），需通过轮询接口或 WebSocket 呈现细分进度：`上传完成 -> 版面分析与表格识别 -> LLM 提取表格摘要 -> 向量切块与入库完成`。


2. **解析内容与切块预览**
* **结构化渲染**：引入 `marked.js` 等渲染引擎，将后端返回的 Markdown 渲染为标准富文本，尤其保证复杂多列表格的完整展示与横向滚动支持。
* **切块调试视图（可选/管理端）**：高亮展示哪些区域被识别为“独立表格”、哪些被划分为“正文父子块”，便于校验切块合理性。


3. **问答交互与溯源（Grounding）**
* **流式交互（SSE）**：接收后端推流（Server-Sent Events），实现大模型打字机效果。
* **参考来源展开卡片**：展示模型回答所引用的溯源信息（包括 PDF 页码、章节标题及命中的完整表格/段落片段）。



---

### 二、 后端（Backend）职责

后端充当调度中枢，负责**业务逻辑**、**任务解耦**、**元数据持久化**与**上下文拼装**：

1. **API 网关与路由控制**
* `POST /api/documents/upload`：保存上传文件至临时或持久化存储（如 MinIO/S3/本地文件系统），生成全局唯一的 `doc_id`。
* `POST /api/chat`：接收用户 Query，调度检索与大模型推理，以流式（Streaming Response）向前端输出。


2. **异步流水线编排**
* 采用异步任务调度（FastAPI `BackgroundTasks` 或 Celery/Redis），避免长时间阻塞 HTTP 请求。
* 调度链路：调用 AI 解析器 -> 接收 Markdown AST -> 提取表格并触发摘要任务 -> 触发正文父子切分 -> 批量写入向量库。


3. **双存储引擎管理**
* **关系型/元数据库（PostgreSQL / SQLite）**：存储完整文档记录、父块文本映射（`parent_id` 映射到 `parent_text`）、原始表格 Markdown 映射（`table_id` 映射到 `table_markdown`）。
* **向量数据库客户端（Qdrant / Chroma / Milvus）**：负责向向量集合（Collections）中写入密集向量与检索过滤标量（`doc_id`, `type`, `page`）。


4. **上下文解包与 Prompt 组装**
* 拿到向量库召回的子块或表格摘要后，**在后端进行“以小换大”的还原查找**：通过 `parent_id` 或 `table_id` 从元数据库取出对应的完整父段落或完整 Markdown 表格。
* 将检索内容、用户 Query 与对话历史合并填入系统 Prompt 模板，控制上下文总 Token 预算。



---

### 三、 AI 管道（AI Pipeline）职责

AI 部分专注于**特征提取**、**语义索引**、**相关度排序**与**内容推理**：

1. **版面感知解析器（Layout-Aware Parser）**
* **工具**：Docling 或 MinerU。
* **职责**：执行版面分析（检测栏目边界、阅读流顺序、页眉页脚过滤）与表格拓扑识别（提取跨行跨列结构并输出为标准 Markdown/HTML 表格）。


2. **切分与数据路由模块（Chunker & Router）**
* **表格路由**：正则或语法树剥离所有表格块，作为独立不可分割的原子单元。
* **正文父子分块**：先基于 Markdown 标题层级切分为 800–1,200 Token 的父块；再使用重叠滑动窗口在父块内划分为 200–300 Token（Overlap 30 Tokens）的检索子块。


3. **辅助提炼模型（Lightweight LLM for Summary）**
* **职责**：对表格原子块运行自然语言摘要 Prompt，输出该表格的统计指标、列维度、主题范围等 100 字语义文本，用于替代直接向量化生硬的数字网格。


4. **向量表征与重排（Embedding & Reranker）**
* **Embedding 模型**：对“正文子块”和“表格摘要”统一计算稠密向量（Dense Embeddings）。
* **Reranker 模型（如 BGE-Reranker）**：在向量库初筛召回 Top-20 候选后，对 Query 与候选块进行交叉编码重新打分，选出最相关的 Top 3–5，进一步提升精度。


5. **最终推理大模型（Generator LLM）**
* 依据拼接的完整父块与原始表格回答用户问题，严格执行“基于所给文档作答，无信息则声明未知”的事实约束。

     │                               │── 5. 表格求摘要 / 正文切父子 ───>│                             │
     │                               │<── 6. 返回摘要与子块 ───────────│                             │
     │                               │                                 │                             │

     │                               │<── 8. 返回高维向量 ─────────────│                             │
     │                               │                                 │                             │

     │                               │── 10. 保存子块向量/摘要向量 ──────────────────────────────────>│ (向量库 Qdrant)

### 五、 落地执行排期与验证标准

1. **数据流水线打通（Day 1–2）**
* 完成 Docling 解析、Markdown 提取、表格抽离与子块切分的独立脚本。
* 验证：抽取 3 份含复杂跨列大表的 PDF，确认导出的表格没有丢失表头与数字。


2. **存储与索引联调（Day 3）**
* 本地启动 Qdrant/Chroma 和 SQLite，编写批量插入逻辑（向量入库，关联 ID 写入 SQLite）。
* 验证：通过检索命中一个子块后，单次 SQL 查询能否稳定取回该子块所属的完整 1,000 Token 父块。


3. **后端 API 与编排整合（Day 4）**
* 用 FastAPI 实现 `/api/documents/upload` 与 `/api/chat`，接入 Reranker 与 LLM 流式输出。
* 验证：使用 Postman 或 curl 发送问答请求，验证 SSE 流式输出是否连贯。


4. **前端看板与界面拼装（Day 5）**
* 基于提供的单文件模板接入后端接口，实现上传进度展示、双栏 Markdown 渲染和流式问答对话框。
